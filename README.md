# SaveHatke AI

An AI assistant platform with a public homepage, Google-gated sign-in, a user
dashboard, and API keys for authorized accounts. Its answers are generated by a
**real open-weight language model that runs entirely in the user's browser**
over WebGPU — no prompt is ever sent to a third-party AI API.

Access is controlled by a **Google Sheet whitelist**: only accounts listed as
`active` can reach the assistant, the dashboard, or `/api/chat`.

## How it works

```
browser → session cookie → identity check → whitelist check
   ├─ GET  /api/ai/config   → non-secret model config (server-owned)
   └─ on-device WebGPU model (WebLLM)  → streamed reply   [primary]
          └─ fallback, only if no WebGPU AND a self-hosted runtime exists:
             POST /api/chat (server) → self-hosted OpenAI-compatible model
```

- Sign-in is **Google OAuth 2.0 (authorization code + PKCE)** only. There is
  deliberately no email/password path — the site never handles a password.
- The session lives in an **HttpOnly cookie** that JavaScript cannot read. The
  browser holds no model credentials.
- Authorization is re-checked against the whitelist on every protected request,
  so revoking an account in the Sheet takes effect within the cache TTL, even
  though the user's cookie is still cryptographically valid.
- The page gate (`middleware.js`) and the API gate (`lib/authorize.js`) are
  independent, so bypassing one still gets a 401/403 from the other.

## The AI model (primary path)

SaveHatke AI runs a **real open-weight instruction model on the user's own
device** through [WebLLM](https://github.com/mlc-ai/web-llm) over **WebGPU**.
The default model is `Qwen2.5-1.5B-Instruct` (MLC `q4f16_1` quantization). The
library is vendored at this origin (`public/vendor/web-llm/`) and served under
the app's own `script-src 'self'`; the model itself is downloaded once from the
configured model host and cached by the browser for later visits.

This is genuine text generation, not a rule/keyword engine:

- **Prompts never leave the device.** Inference happens in a Web Worker on the
  local GPU. There is no server inference and **no third-party AI API** (no
  OpenAI/Gemini/Anthropic/etc.) in the request path.
- **Real streaming** with stop, regenerate, copy and thumbs feedback; bounded
  **context** assembly with a running summary of trimmed-off turns; optional,
  user-controlled **memory**; and a deterministic **calculator tool** whose
  verified result is handed to the model instead of trusting its mental math.
- **The model layer is replaceable.** The UI depends only on the `AIEngine`
  interface (`public/ai/engine.js`), so the model can be swapped — a larger
  on-device model, or a self-hosted server runtime — without any UI change.

### Honest capability gating

The client probes WebGPU before offering on-device inference (`public/ai/capabilities.js`):

- **WebGPU available** → the model loads on device and generates locally.
- **No WebGPU, but a self-hosted runtime is configured** (`SAVEHATKE_MODEL_API_URL`)
  → it falls back to that runtime via `/api/chat`. It **never** falls back to a
  rule-based engine, and never pretends the on-device model answered.
- **No WebGPU and no fallback** → the UI says so plainly and disables input,
  rather than faking a reply.

Requirements to actually generate on device: a **WebGPU-capable browser**
(recent Chrome/Edge, Chrome on Android, or Safari 17+ with WebGPU enabled),
hardware acceleration on, and a one-time model download (~1 GB, then cached).

## The server fallback engine

`POST /api/chat` remains as the **server-side fallback path** for devices that
cannot run WebGPU (used only when `SAVEHATKE_MODEL_API_URL` points at a
self-hosted, OpenAI-compatible runtime). It is also still backed by **SaveHatke
AI**, a small custom retrieval/rule engine built for this domain — CPU-only, no
API key, no GPU, no dependencies. That engine is intentionally **not** presented
to the browser as "the AI": the primary generator is the on-device model above.

```
message
  ↓ securityEngine.inspectInput    refuse disclosure attempts first
  ↓ contextManager                 recall the previous turn
  ↓ intentEngine                   intent + entities + confidence
  ↓ toolRouter                     live data, session-scoped identity
  ↓ knowledgeEngine                policy and documentation answers
  ↓ responseEngine                 compose from evidence only
  ↓ securityEngine.inspectOutput   scrub anything that must not leave
  reply
```

Two invariants shape the design:

- **The engine is not the authority.** Every fact about an account or the
  marketplace comes from the application API (`AI_API_BASE_URL`), called with
  the caller's own session cookie. When that call fails the engine says so. It
  never invents a listing, an amount, a status or a date.
- **A blocked request never reaches the intent layer.** Refusing before
  classification means an injection attempt cannot influence which tool would
  have run.

Which engine answers is chosen by `AI_PROVIDER`, not by the browser. The
response shape is always `{ reply, source }` and the frontend only reads
`reply`, so switching engines — including back to an upstream model — needs no
frontend change.

### Model

A TF-IDF nearest-neighbour cosine classifier over per-intent training examples,
plus a hand-written rule layer that *rescues* the classifier when it is unsure
(and can never overrule it when it is confident). Vocabulary IDF is computed per
intent rather than per example, which is what stops words shared across intents
from looking distinctive.

Confidence is three-tier: **≥ 0.80** high (tools may run), **≥ 0.55** medium
(tools run only when a rule also matched), **below** that the engine asks a
clarifying question and runs nothing.

## The training pipeline

```bash
npm run ai          # build → evaluate → smoke test
npm run ai:build    # prepare → vocabulary → train
npm run ai:eval     # score the held-out sets; exits non-zero on any failure
npm run ai:test     # readable per-capability smoke test
```

Training never runs inside a request. Model files are committed and loaded once
per warm instance, so a cold start still answers immediately.

`scripts/ai/prepareData.js` fails the build on anything resembling real user
data (emails, keys, JWTs, long digit runs). Synthetic addresses are permitted
only on `example.com/net/org` and `savehatke.com`.

`ai:eval` records a content fingerprint of every fixture in `compiled.json` and
**refuses to score a stale artefact** rather than reporting an accuracy that
describes an older revision.

## Configuration

Copy `.env.example` to `.env.local` and fill it in:

```bash
cp .env.example .env.local
```

`.env.local` overrides `.env` (the Vercel convention), and a value exported in
the shell overrides both. Six variables are required — `GOOGLE_CLIENT_ID`,
`GOOGLE_CLIENT_SECRET`, `SESSION_SECRET`, `GOOGLE_SHEET_ID`, and either
`GOOGLE_SERVICE_ACCOUNT_EMAIL` + `GOOGLE_PRIVATE_KEY` or a single
`GOOGLE_SERVICE_ACCOUNT_JSON`.

**Every variable is documented inline in `.env.example`, and the full setup
walkthrough — Google Cloud, the Sheet layout, Vercel deployment, granting and
revoking access, and the security review — is in [`AUTH-SETUP.md`](AUTH-SETUP.md).**

The engine needs no configuration to work: it ships with its model files and
answers out of the box. Two optional variables matter:

- `AI_API_BASE_URL` — the SaveHatke application API used for live data. Until
  it is set, coupon search, earnings, payouts, purchases and tickets answer
  "I could not retrieve that information" rather than guessing.
- `AI_PROVIDER` — `SAVEHATKE_AI` (default) or `UPSTREAM_MODEL`.

Misconfiguration is reported once per process, on the first turn, rather than
degrading silently — an unset `AI_API_BASE_URL`, a disabled engine, a bypassed
engine or an inverted confidence pair each print a `[savehatke][ai] config:`
line to the server log. This matters most for the first case: with no API URL
set, every account question still returns a tidy, confident-sounding reply and
nothing else in the system looks wrong.

## Testing

```bash
npm test              # everything below, in order
npm run test:ai       # tests/ai.test.mjs — engine safety suite
npm run test:ai-live  # tests/ai-live.test.mjs — live-data path, stub API
npm run test:backend  # tests/backend.test.mjs — backend checks
npm run test:e2e      # verify.mjs — browser checks
npm run shots         # render pages to shots/ for visual review
npm run ai:eval       # engine accuracy against the held-out sets
```

The engine suites need no network, no credentials and no browser: the tools
report `unavailable` and the engine must degrade honestly. `ai-live.test.mjs`
starts its own stub application API on a random port, so the live path —
identity forwarding, payload parsing, earnings arithmetic — is exercised for
real rather than assumed.

The end-to-end suite drives real Chrome. It starts its own server (so it can
control the whitelist through `SAVEHATKE_WHITELIST_STUB`) and **refuses to run if
port 8931 is already in use** — stop your dev server first. No suite needs
real Google credentials.

Honest account of what is confirmed and what still needs a WebGPU browser.

**Confirmed in this environment (automated):**

- `npm run test:ai` — 173/173 pass (engine safety: injection, disclosure,
  permissions, and the static-exposure guard that no engine internals leak into
  `public/`).
- `npm run test:ai-live` — 40/40 pass (server fallback/live-data path).
- `npm run test:backend` — 110/110 pass (auth model, gating, session cookies).
- The dev server serves `chat.html` (auth-gated → redirects to login when signed
  out), the ES modules under `public/ai/`, and the vendored WebLLM runtime;
  `GET /api/ai/config` correctly returns `401 unauthenticated` to a caller who is
  not signed in.

**Requires a WebGPU browser to confirm (cannot run headless in CI/CLI):**

- The end-to-end **on-device generation** — model download progress, streamed
  tokens, stop/regenerate, and Markdown/code rendering — must be verified by
  signing in as a whitelisted user in a WebGPU-capable browser and sending a
  message. The ~1 GB model download happens once, then is cached.
- Until that check is done in such a browser, treat on-device generation as
  *implemented and wired* but *not yet observed end-to-end here*.

**Not implemented (documented, not faked):**

- Full Google Sheets write layer and the `Conversations`/`Messages`/`Memory`/
  `Usage`/`Feedback`/`ToolCalls`/`Errors` tabs. Memory and feedback are
  currently **browser-local** and the UI says so; server-side persistence is a
  documented next step, not silently pretended.
- Multi-conversation history, an admin area, file/code upload analysis, and web
  search are not built. The system prompt forbids the model from claiming it
  browsed the web or opened a file.

## Deployment

Deploys to Vercel as static files plus Edge/Node functions. `outputDirectory` is
`public/`; set every variable from `.env.example` in the project environment.

The on-device model needs the browser to fetch the WebLLM runtime (same-origin)
and the model files (from the model host). `vercel.json` is configured for this:
`script-src` allows `'wasm-unsafe-eval'` (WASM compilation), `worker-src`/`child-src`
allow the module/blob worker, and `connect-src` allows the HuggingFace/MLC model
hosts. If you set `MODEL_HOST` to a self-hosted mirror, add that origin to
`connect-src` too.

`vercel.json` pins `includeFiles` for `api/chat.js`: the server fallback engine
reads its model and data files from disk with `fs`, so they must be bundled with
the function explicitly. Nothing under `server/` or `data/` is ever served
statically.

## Design notes

- Plain HTML, CSS and vanilla JS for the app shell. No framework and no build
  step. The only non-first-party network request is the **one-time model
  download** for the on-device AI (from the configured model host, then cached);
  prompts and replies never leave the device. Point `MODEL_HOST` at a self-hosted
  mirror to remove even that third-party dependency.
- The homepage opens on a dark hero band with a transparent fixed header;
  `core.js` switches the header to the light frosted bar once the hero scrolls
  past. Style dark-header overrides as `:not(.is-scrolled)` so they don't leak
  into the scrolled state.
- Design tokens live at the top of `styles.css`. Dark surfaces use the `--dark*`
  and `--accent-on-dark` tokens.
- Animations are `IntersectionObserver`-based and respect
  `prefers-reduced-motion`. Responsive breakpoints: 900px and 720px.
